# Workflow Test Authoring

You are authoring AI Studio workflow tests from a local assistant session. Do not call backend Builder agent APIs for test generation, data generation, JSON repair, or test-data compaction. For judge grading, the default `local` provider uses the local judge request and attach flow; do not call backend Builder APIs yourself in that route. The explicit `--judge-provider remote` route is the supported noninteractive way to ask the configured FA environment to judge semantic results. Unless the user explicitly requests remote judging, never pass `--judge-provider remote` to `run-workflow-test`, `run-workflow-tests`, or any optimization sweep command — this applies regardless of workspace type (legacy or app-package). Never use `npm run` or `npm test` to execute tests or sweeps; always call the CLI binary directly.

Use the CLI as deterministic tooling:

1. After any successful workflow create or material edit, start with `aistudio get-workflow-test-sync-plan --file <workflow.wf>`; it is the automatic inventory plus scenario source and includes existing tests plus a ready baseline when available.
2. Do not call `aistudio get-workflow-test-context --file <workflow.wf>` immediately after `get-workflow-test-sync-plan` as a routine step. Call it only when a specific non-judge authoring decision cannot be made from the sync plan output, such as needing exact node input parameter names or output field names. Semantic judge authoring uses the narrower `get-workflow-test-judge-context` flow below.
3. Run `aistudio get-workflow-test-scenarios --file <workflow.wf>` only when you need the raw scenario suggestions separately from the sync plan.
4. Generate one local workflow test definition JSON object when the test needs model-authored assertions, input, rubric, notes, path assertions, or model-generated `testData`. If you write it to disk, use a scratch path such as `.debug/<test-name>-definition.json`, not the final `test/workflows/...` output path.
5. Materialize the source-controlled test with `aistudio do-generate-workflow-test --file <workflow.wf> --test-name <name> --prompt "<intent>" --data-capture-policy record-later|record-now|model-generated|baseline-replay --definition @.debug/<test-name>-definition.json`. When a ready recorded baseline exists for a model-generated scenario, pass `--base-test-file <ready-test-file>` and include only `testDataOverrides` in the definition. For trigger-context-only variants that reuse the same data path, use `baseline-replay` with `--base-test-file` and no `testDataOverrides`.
6. Refresh an existing matching test with `aistudio do-update-workflow-test --file <workflow.wf> --test-file test/workflows/<lowercase-workflow-code>/<test-name>.json --definition @.debug/<test-name>-definition.json`; preserve valid `testData` unless the scenario needs replacement data or minimal overrides.
7. Run one test with `aistudio run-workflow-test --test-file test/workflows/<lowercase-workflow-code>/<test-name>.json --data-source file|live --evaluation-mode deterministic|hybrid`.
8. Run a workflow suite with `aistudio run-workflow-tests --workflow-code <workflowCode>`. Run an app-scoped suite with `aistudio run-workflow-tests --app-file <app-file>` or `aistudio run-workflow-tests --app-code <appCode>`. Use bare `aistudio run-workflow-tests` only when the user explicitly asks for all workspace tests, full regression, or CI-style validation.

## Semantic Judge Authoring

For every new sync-plan scenario whose `authoringHints.judgeAuthoringContext.semanticNodes` is non-empty, the model must author `definition.judge`; the CLI does not synthesize the semantic contract. Follow this sequence before `do-generate-workflow-test`:

1. Read the focused sync-plan action's compact `authoringHints.judgeAuthoringContext`. Use its scenario intent, invocation, ordered path, semantic-node roles, terminal contribution, grounding policy, and contract hashes as the factual index.
2. Treat `terminal-output-owner` nodes as the primary semantic contract. A `terminal-output-candidate` is the closest on-path semantic node when explicit output lineage cannot prove ownership. Treat `upstream-semantic` nodes as supporting grounding context only. Do not merge every on-path prompt into one judge contract and do not include semantic nodes listed under `excludedSemanticNodeCodes`.
3. For each terminal owner or candidate, run `aistudio get-workflow-test-judge-context --file <workflow.wf> --scenario-id <scenario-id> --node-code <node-code> --detail full`. The command returns the complete prompt, system prompt, output specifications, dependency path, and downstream transformations without truncation. If a compact field contains a retrieval reference, retrieve it before authoring criteria; never infer omitted content from its hash or length.
4. Write a concise scenario-specific `judge.expectedOutcome` and independent `judge.rubric` items. Judge the final observable output contract, required transformations, and grounding in replayed or recorded evidence. Use upstream semantic prompts only when their output contributes to the terminal result. Do not copy path assertions into the rubric and do not require internal wording that is not part of the final contract.
5. Pass the complete judge object in the scratch definition. The CLI adds compact `judge.authoring` provenance with semantic node codes, terminal owners, scenario ID, and contract hash. Do not hand-author that provenance.

Existing tests are non-migrating. Running, recording, syncing, or refreshing reports must preserve their current judge exactly, including tests with no `judge.authoring` metadata. If the sync plan reports `judgeContractState: "changed"`, explain that review is available but do not update the judge unless the user explicitly asks to review or repair it. For an explicit judge update, retrieve current judge context again and send only the intended judge changes through `do-update-workflow-test`; the CLI then records fresh provenance.

Mode selection matters. If the user asks to show, inspect, preview, display, or get the workflow test sync plan, run `get-workflow-test-sync-plan --file <workflow.wf>` and stop after explaining that read-only plan. Do not generate, update, record, run, or judge tests for a preview request. If the user asks to run, execute, generate, regenerate, sync, create/update tests, or complete the workflow test sync plan, treat it as execution mode and complete the sync loop below unless a real blocker or required user decision stops execution.

In automatic sync mode, do not call a workflow test generated just because the JSON file exists. A useful generated workflow test has ready `testData` or a recorded/generated data blocker that was actually attempted and reported. For `record-now` actions, attempt live recording. For `model-generated` actions, embed generated `testData`. For `baseline-replay` actions, require the referenced base test to be ready first. If recording is blocked by auth, missing data, workflow errors, or environment errors, report that blocker explicitly with the workflow, test name, and command that remains blocked.

A workflow sync loop is complete only when every action in the current workflow sync plan has reached one of these terminal states: source-controlled test exists with ready data and the workflow suite passes, the suite fails with a concrete failure reason, a local judge request remains pending with its request path and attach command, or a concrete blocker is reported with workflow code, test name, blocked command, and reason. Do not leave scratch definitions in `.debug/` as the only evidence of generated tests, and do not move to the next app backing workflow while supported actions in the current workflow are still merely listed as required commands.

When the user asks to run or complete a workflow test sync plan, never answer by only summarizing `get-workflow-test-sync-plan` output. If the plan has `missing` or `outOfSync` create/update actions, continue executing the recommended actions in the same turn. Stop only for a real command failure, auth recovery, missing required user input, or another blocker that prevents command execution.

For every recommended create or update action, finish the materialization step before moving to the next action. If you write `.debug/<test-name>-definition.json`, immediately run `aistudio do-generate-workflow-test --file <workflow-file> --test-name <test-name> --prompt "<purpose>" --data-capture-policy <policy> --definition @.debug/<test-name>-definition.json` or the matching `do-update-workflow-test` command for update actions. Then verify the source-controlled `test/workflows/.../<test-name>.json` file exists. A scratch definition file is only temporary authoring input; it is not a generated test, not a blocker, and not a stopping point. Do not report "tests generated" until the source test file exists and its required `testData` state is ready, pending with a concrete attempted recording blocker, or failed with a concrete command error.

The sync plan may include input-aware path metadata. Use it to decide what needs live proof before a scenario-backed test is trusted:

- `pathSource: "predicted"` means the path came from topology only. It is advisory, not final proof. If live execution contradicts it, refine the scratch definition's `pathAssertions` from the observed runtime path instead of forcing the topology guess.
- `pathSource: "input-derived"` means the path was derived from trigger input, run profile input, or condition/switch expression analysis. Treat it as a high-confidence candidate. If `requiresRuntimePathValidation` is true, run or record with the exact sync-plan `suggestedInput` before treating the path as proven. If live execution contradicts it, report an input/routing mismatch with the observed path and the relevant `inputDependencies`; do not silently rewrite it as if the candidate had been proven.
- `pathSource: "observed"` means a previous live execution path binding is current for the same normalized input and workflow definition. You may use it as authoritative.
- `pathSource: "user-specified"` means the user described the path or routing intent. Treat it as a candidate until live execution proves it. If the observed path matches, write the scenario-backed test with the observed path. If it does not match, report the divergence, offer a custom test if the user still wants that assertion, and do not persist an incorrect scenario-backed path.

When an action includes `inputDependencies`, read them before authoring input or path assertions. They explain which runtime parameter and value the workflow branch depends on, such as `parameters.prjPjfRoutingContext = "redwoodui"`. Preserve the sync-plan `suggestedInput` exactly for these scenarios unless the user explicitly provides a different runtime input. Exception: when `inputGuidance.useSuggestedInput` is `false` for an advisory primary chat input, interpret the current action's `routingDecisionContext` and provide an explicit model-synthesized `definition.input` instead of preserving the fallback. For Query app-stage scenarios, preserve the trigger envelope fields but synthesize `input.message` per the Query message precedence below; do not treat the CLI's default empty message as intentional. Do not replace REST parameters with empty schema defaults. If the user asks to use a run profile, that user instruction takes precedence over inferred values. For REST-trigger and input-dependent secondary scenarios, inspect the supported REST trigger input parameters, matching run profiles, `inputDependencies`, and the `CONDITION` or `SWITCH` expressions on the intended scenario path before writing `input.parameters`. Populate the specific parameters that route the workflow to that scenario; do not rely on a generic message-only input when the branch depends on REST parameters, active conversation state, chat history, attachment context, or other runtime fields. If the required runtime context cannot be inferred from the sync plan, run profile, workflow purpose, or user prompt, classify that scenario as blocked input context or ask for the missing value instead of generating a misleading test.

When the sync plan marks scenarios with `primaryClass: true` and `requiresRuntimePathValidation: true`, complete those primary-class live validations first. Do not generate a large set of secondary branch, data, or edge-case tests while every primary-class route remains unproven. If the sync plan says secondary scenarios were suppressed by primary validation gating, generate or record at least one valid primary-class scenario, rerun the sync plan, then continue with the remaining actions.

When primary coverage is pending, start with the compact `get-workflow-test-sync-plan --file <workflow-file>` text output and its action table. If the primary action's `inputGuidance.useSuggestedInput` is `false` and `routingDecisionContext` is present, immediately call `get-workflow-test-sync-plan --file <workflow-file> --recommended-batch-only true --format json` before generating that action. Interpret only the current action's `routingDecisionContext`, including each raw condition or switch expression and expected outcome, then provide an explicit natural scenario-specific `definition.input`; the workflow-derived `suggestedInput` is advisory and must not be copied as an exact input. Do this synthesis before the first test run. If the primary action has an exact user, run-profile, REST, app-stage, or expression-derived input, preserve that exact input and do not replace it through model synthesis. The focused view intentionally omits the large path assertion arrays while retaining the current action's authoring hints. For scenario-backed create actions, `do-generate-workflow-test` derives the sync-plan path assertions from the test name. Whenever `expectedPath` is absent from the current sync plan output for an action, whether in compact text/table format (primary coverage) or in `--recommended-batch-only` JSON (secondary next action), omit `pathAssertions` from the scratch definition entirely. The CLI rehydrates the correct path assertions from the scenario id or test name. Do not hand-author partial or alternate `mustExecute`/`mustNotExecute` arrays. The only exception: if the full plan JSON explicitly includes `expectedPath` for an action, you may copy it exactly, never shorten it or omit `mustNotExecute`. There are two primary coverage phases. First generate and live-record the executable `record-now` primary action, then immediately run `aistudio run-workflow-test --test-file <path> --data-source file` to evaluate it. A sync plan showing `upToDate` after generation does not mean the test has been run and evaluated — it only means the test file exists with ready testData. This applies to any generated or updated test, not just primary-phase ones: for every hybrid test (`defaults.evaluationMode: "hybrid"`), generating the file is never sufficient — you must run it and, if it returns `needs-judge`, write the local judge result and attach it with `attach-workflow-test-judge-results` before doing anything else. Only after the test has a definitive run status (passed, or judge attached and confirmed) should you rerun the sync plan. Only after that ready recorded baseline exists should you generate any primary-class `baseline-replay` action that depends on it. Do not try to generate a `baseline-replay` primary action before the refreshed sync plan gives it a concrete `baseTestFile`. Secondary paths come only after both primary phases are current or explicitly blocked. After a primary-phase `run-workflow-test` returns `passed` or `needs-judge`, and after `attach-workflow-test-judge-results` completes, rerun `get-workflow-test-sync-plan --file <workflow-file>` (text format, without `--recommended-batch-only`) to confirm primary coverage status before taking any further action. Do not call `get-workflow-test-final-summary` or `run-workflow-tests` at this point — the sync plan must confirm `primaryComplete: true` and `finalSummaryAllowed: true` before either of those commands is valid.

After primary-class validation passes, do not stop just because the refreshed sync plan reports a large number of secondary scenarios. If the sync plan includes `coverageExecution.nextActionIds` or `coverageExecution.nextActions`, that list contains the single required next action, not informational output. Run `get-workflow-test-sync-plan --file <workflow-file> --recommended-batch-only true --format json` to get the focused compact work queue, then execute the create/update action in `coverageExecution.nextActions`. Use `coverageExecution.costClass` and each action's `costClass`/`lowRisk` fields when deciding whether the action is cheap, standard, or complex. Use the action's `authoringHints` as the compact authoring source: `pathComplexity`, `targetBranch`, `inputGuidance`, `dataGuidance`, and `validationGuidance` describe the intended branch, input shape, data reuse policy, and repair boundary without requiring full path assertion JSON. Do not infer action cost or scenario intent by reading or copying full `expectedPath` arrays; the focused view intentionally omits those heavy fields. For branch-path and switch-value actions where dataCapturePolicy is record-now: treat authoringHints.dataGuidance.branchForcingHints as input-construction guidance for the live recording, not as synthetic testData instructions. The hints describe what input parameters or context state triggers the target branch outcome in the live environment. Construct input.parameters, input.message, and trigger-context fields to match those hints, then attempt live recording. Do NOT carry forward accumulated workflow state (active-request stage, pending-decision context, prior LLM classification state) from a baseline test or from another branch scenario unless the hints explicitly require it. If `authoringHints.pathComplexity` is `deep-semantic`, treat the case as a semantic route, not a simple fallback: author a focused user input and generated data that drive the listed target branch, preserve the scenario id in the definition metadata, run the generated test, and repair only the current test once if the input or data clearly missed the intended branch. If a secondary test fails semantic judging, report that failed test and continue unrelated secondary tests; semantic failure means the workflow or expectation needs review, but it does not invalidate the baseline data path for other scenarios. For every secondary path scenario, regardless of `dataCapturePolicy`, if the first generated, updated, recorded, or replayed attempt misses the intended branch, try one different input before deferring only that scenario. The second input must materially change `input.message`, trigger parameters, run-profile fields, active context, or branch-forcing test data; rerunning the same input does not count. After 2 total failed attempts, call `mark-workflow-test-unable-to-generate` and include both attempts in the blocker payload with the input used, observed branch, expected branch, and why the second input was chosen. The sidecar command records a deferred scenario, not a workflow-level blocker. For secondary record-now branch tests, also apply the observed-path model: if the intended branch was taken, update path assertions from `result.run.nodeResults` keys (mustExecute) and the filtered sync-plan mustNotExecute; retry with different input via `do-update-workflow-test` up to 2 total attempts if it was not; call `mark-workflow-test-unable-to-generate` and skip only that scenario after 2 failed attempts. Immediately rerun `get-workflow-test-sync-plan --recommended-batch-only true --format json` after any deferred scenario. Do not call get-workflow-test-final-summary while any unrelated create or update actions remain. If a secondary test fails deterministic path assertions, defer only that scenario and directly dependent scenarios after the required second input attempt; continue unrelated recommended actions. A failed secondary suite is not a final stopping condition while the refreshed sync plan still has unrelated create/update actions; rerun `get-workflow-test-sync-plan --recommended-batch-only true --format json`, execute the next unrelated action, and carry the failed secondary tests forward as reported failures. If a primary-class test fails, stop and report the blocker because secondary coverage depends on current primary proof. When reporting a failed test, surface the CLI's natural-language suggested prompt from the suite summary or report. Do not show raw underlying commands to the user unless they explicitly ask for command syntax. Live recording by itself is not a user-decision gate. For `record-now` actions, attempt live recording and classify auth, missing data, workflow, or environment failures as scenario-level deferred entries when the failure is local to one scenario. Do not pre-block secondary scenarios merely because the path may execute mutating BO, tool, deeplink, workflow, or write-like nodes. A user request to run or generate the sync plan is approval to attempt supported recording and test execution; if the path mutates data, report that fact in the final summary. Stop before execution only for workflow-level blockers such as auth recovery, missing required input, backend/runtime error, no safe next action, or unavailable environment data. After each action, run, repair, judge attachment, or deferred scenario completes, rerun `get-workflow-test-sync-plan --recommended-batch-only true --format json` immediately. If it returns another action in `coverageExecution.nextActionIds`, continue without asking. Only call `get-workflow-test-final-summary --file <workflow-file>` after a sync plan response explicitly shows `finalSummaryAllowed: true`. Do not call it speculatively to check whether the loop is done — always rerun the sync plan and confirm `finalSummaryAllowed: true` before calling it. Never mention internal cost units, cost-unit budgets, scores, or hidden scheduling math to the user. If the user explicitly asks for exhaustive coverage or all tests, continue action by action until every supported action is complete, generated and failing, or deferred.

Distinguish plan display from plan execution. If the user asks to show, inspect, or explain the sync plan, display the plan and stop. If the user asks to run, execute, regenerate, or complete the sync plan, keep looping until the sync plan reports `finalSummaryAllowed: true`. While `syncLoopState` is `actions-remaining`, execute the single action in `coverageExecution.nextActionIds`, rerun `get-workflow-test-sync-plan --recommended-batch-only true --format json` (once primary coverage is confirmed), and continue. Do not call `get-workflow-test-final-summary` while `finalSummaryAllowed` is false. Also do not call `run-workflow-tests` (full suite) while `syncLoopState` is `actions-remaining` or `finalSummaryAllowed` is `false` — it is not a valid diagnostic step during an active sync loop. The sync loop uses `run-workflow-test` (single test) to validate each individual generated test; a full suite run is only appropriate after `finalSummaryAllowed` is `true`. If `syncLoopState` is `deferred-only` and `finalSummaryAllowed` is `true`, call the final-summary command and report the deferred scenarios; do not describe this as a whole workflow sync blocker. If `syncLoopState` is `deferred-only` but `finalSummaryAllowed` is `false`, rerun `get-workflow-test-sync-plan --recommended-batch-only true --format json` to pick up any remaining actions before calling the final-summary command. The `summary.deferred` count in the sync plan is a cumulative historical record of scenarios deferred by `mark-workflow-test-unable-to-generate` in earlier loop iterations. It is not a current blocking condition and must not influence whether the loop continues. A sync plan with `syncLoopState: 'actions-remaining'` must execute the next action in `nextActionIds` regardless of how large `summary.deferred` is. Do not produce user-facing text, stop the loop, or treat the loop as blocked because this count is greater than zero. The sync loop has exactly three valid stopping conditions: (1) a CLI command returned a hard failure — non-zero exit, authentication error, or a missing required file that prevents the next action from being attempted; (2) the user explicitly asked to stop; (3) `syncLoopState` is `'ready-for-final-summary'` and `finalSummaryAllowed` is `true`. Every other condition does NOT justify pausing or producing any output: consecutive deferred scenarios of any type, a large number of remaining actions (10, 20, or 49 are all normal), repeated path-divergence failures across multiple scenarios, completing a recognizable phase such as primary coverage or the first batch of secondary scenarios, a judgment that the loop has become long or repetitive, or an instinct to summarize partial results before continuing. Execute every action in `coverageExecution.nextActionIds` in sequence without interruption, without intermediate progress reports, and without returning control to the user until one of the three stopping conditions above is true.

During an active sync loop, do not output any user-facing text between tool calls. Each tool invocation must be immediately followed by the next tool call without intermediate explanation, narration, or commentary. The only permitted text output during a sync loop is the final response produced after `get-workflow-test-final-summary` has been called and `finalSummaryAllowed` was `true` in the preceding sync plan output. Do not call `aistudio --help`, `aistudio <command> --help`, or any command discovery during an active sync loop. There is no batch executor for secondary scenarios — the sync loop processes one action at a time by design. Do not search for an alternative executor or a higher-level command. If `coverageExecution.nextActionIds` contains an action, execute it directly.

After primary coverage is confirmed (`primaryComplete: true` in the sync plan), never run `aistudio get-workflow-test-sync-plan` without `--recommended-batch-only true --format json`. The full text sync plan for a large workflow exceeds 50 KB per call and exhausts the context window after a few iterations; the batch JSON view is under 15 KB and contains the same `coverageExecution.nextActionIds` and `guidance.nextStep` the loop needs. The only exception is diagnosing a hard error that the batch JSON does not explain. When processing multiple workflows, complete all non-blocked secondary actions for one workflow before checking another workflow's sync plan.

When `get-workflow-test-final-summary` is valid because no create or update actions remain in the sync plan, call `get-workflow-test-final-summary --file <workflow-file>`. Compose the final response with the workflow creation, change, test-generation, or run outcome first, followed by a section named exactly `Validation and Insights`. Preserve the command's test counts, workflow suite `Report:` link, `Metrics:`, and `Optimization:`. Preserve its compact issue count and natural-language next step when failures, pending judges, or unable-to-generate scenarios exist. Do not list every failing or deferred test in the default final response. Use `--format json` only when the user asks for detailed failure diagnostics or structured output. A generated test failure or unable-to-generate scenario does not stop unrelated sync actions; complete the sync loop before producing this final response.

Before classifying a live recording that reached an unexpected fallback branch as an environment data blocker, follow this order: inspect guard expressions, inspect trigger/input shape, inspect generated or recorded `testData` preconditions for the intended branch, then conclude environment data only after those checks pass. A fallback node label describes what branch executed; it does not prove that live data is missing until the workflow routing logic and test input shape are verified.

For condition, switch, code, return, or other expression-bearing node edits, write the inputs patch to a scratch JSON file and pass it with `--inputs-patch @.debug/<name>-inputs.json`. Do not pass inline JSON containing empty-string literals, quotes, `$context`, `{{...}}`, comparison operators, or expression syntax through shell command arguments. Prefer quote-free existence checks for guard conditions when equivalent. After modifying condition guards, run workflow validation or read the workflow back before recording or running tests. If validation passes but runtime routes to an unexpected fallback, read the workflow file directly when the condition node code is known, or use `aistudio get-workflow-test-context --file <workflow.wf>` to inspect condition node inputs and current path assertions. Look for expressions that end with a comparison operator and no right-hand operand, that contain stripped empty-string literals, or that compare against an absent literal, before reporting missing environment data.

When running workflow tests, scope the run to the artifact the user asked about. For one workflow, pass `--workflow-code <workflowCode>`. For one app, pass `--app-file <app-file>` or `--app-code <appCode>` so only that app's active and additional workflow-agent tests run. Do not use bare `run-workflow-tests` for a workflow-specific or app-specific request, because it runs every workflow test in the workspace and can fail on unrelated artifacts.

When the user asks to compare, switch, try, benchmark, or evaluate workflow quality with a different LLM/model, do not edit workflow files or workflow test JSON. First inspect supported choices with `aistudio list-workflow-model-configurations` or `aistudio get-workflow-model-configuration --code <modelConfigurationCode>`, then inspect eligible workflow nodes with `aistudio get-workflow-model-override-targets --file <workflow.wf> --include-ineligible true`. Run existing tests with transient overrides using `aistudio run-workflow-tests --workflow-code <workflowCode>` or the appropriate app-scoped `run-workflow-tests --app-file <app-file>` plus `--model-overrides @file` or the convenience `--model-configuration-code <code> --model-properties @file` flags. Use `--run-label <label>` so model comparison reports are written under isolated `runs/<label>/` or `suites/<label>/` folders and do not overwrite normal reports. For one-test comparison, still use `run-workflow-tests --workflow-code <workflowCode> --test-name <testName>` so a labeled suite report exists for `compare-workflow-test-runs`; do not use `run-workflow-test` alone when a comparison report will be generated.

For fair model quality comparison, prefer recorded `--data-source file` runs when test data is already ready, because each model sees the same replayed BO/REST/tool/vector/deeplink data. Use `--data-source live` only when the user explicitly wants live environment behavior or recorded data does not exist. For semantic outputs from `LLM`, `AGENT`, `MULTI_AGENT`, or LLM-backed `DOCUMENT_PROCESSOR`, compare the final output preview, deterministic routing checks, and judge result/rubric. Do not add deterministic final-output assertions merely because a model comparison was requested. With the default `local` judge provider, do not stop while any selected baseline or candidate case is `needs-judge`: read the run-labeled `.debug/workflow-test-runs/<safe-run-label>/<test-name>-judge-request.json` request, write the matching judge result in that same run-label directory, attach it with `aistudio attach-workflow-test-judge-results --workflow-code <workflowCode> --run-label <label> --cleanup-scratch true`, and continue only after the selected run-labeled suite has 0 failed and 0 needs judge. With `--judge-provider remote`, the CLI calls the configured FA environment default model and completes semantic judging during the run; no local judge result attachment is required. Run `compare-workflow-test-runs` only after the selected baseline and candidate suites have completed. Report duration and any token/cost/usage fields actually emitted by runtime reports; do not invent or estimate cost when reports say token/cost data was not emitted.

The source of truth is one JSON file per test under `test/workflows/<lowercase-workflow-code>/<test-name>.json`. Each test has one single embedded `testData` block. The embedded `workflow.workflowCode` remains the real uppercase workflow code. Create a new test when the user needs a different dataset.

Workflow test `tags` are user-owned test metadata stored in that same source-controlled JSON file. Preserve existing tags during updates unless the user explicitly asks to change them. To set tags at creation time, use `do-generate-workflow-test --tags release-upgrade,smoke`. To update tags on an existing test, use `do-update-workflow-test --add-tags regression`, `--remove-tags smoke`, or `--tags release-upgrade` for full replacement. Tags are normalized to lowercase-kebab by the CLI. Do not invent tags automatically. Recognized conventions are `smoke`, `regression`, and `release-upgrade`, but the CLI does not restrict users to those values.

Use `aistudio run-workflow` or `aistudio run-workflow-chat` only for ad hoc workflow execution. They do not replace workflow tests because they do not manage `testData` recording, replay overrides, deterministic evaluation, local judge requests, suite discovery, or reports.

Users may give a natural-language test goal without exact expected values. Infer the workflow test flow and tool calls. Do not force the user to pick `data-capture-policy`, `data-source`, `evaluation-mode`, or test file paths unless they ask for that level of control.

During workflow authoring, automatic workflow test sync, and self-healing, never read or search local help/static documentation files unless the user explicitly asks you to review those documents. This includes files under local `docs/` folders, help HTML files, architecture Markdown files, copied examples, static pre-built reference documents, and generated report HTML/Markdown used only for human viewing. Do not use these files to discover command syntax, BO/tool codes, node metadata, assertion fields, judge shapes, or workflow-test contracts. Authoritative sources are CLI prompts, direct CLI output, generated workflow/test/report JSON, the CLI-written judge request file including `judgeResultTemplate` and `requiredResultShape`, and `.debug/*-request.json` files generated by the CLI.

Once a workflow-test command has been used successfully or its syntax is already present in this guidance, do not call `aistudio <command> --help` again in the same session unless the command just returned `Unknown option` or `Missing required option`. `input` in a workflow test is the runtime invocation shape sent to the workflow. It always has `message` and may also include `triggerType`, `parameters`, and `singleTurnOnly`. Chat-style tests usually use only a short user-facing `message`. Non-chat tests may have an empty message and should preserve the trigger fields from the sync-plan `suggestedInput` or active run profile. For Agentic App scenarios, use `triggerType: "app"` with `parameters.appHint` such as `Query`, `Summary`, `InitDisplay`, `InitActions`, `InitCommunications`, or `InvokeAction`. For REST-trigger scenarios, use `triggerType: "rest"` with the REST request `parameters` object and `singleTurnOnly: true`; those `input.parameters` values supply the debug API payload, while workflow nodes must read them through `$context.$triggers.REST.$input.<inputName>`. Never derive `input.message` or `input.parameters` from workflow node prompts, LLM task prompts, recordable-node metadata, assertions, path assertions, judge rubrics, compacted data, or `testData`. Do not duplicate REST parameter values into `input.message` just to make a broken workflow pass. Put detailed output requirements in `assertions`, `pathAssertions`, `judge.expectedOutcome`, and `judge.rubric`, not in `input.message`.

For app-stage tests, do not confuse a valid trigger envelope with a complete scenario input. Preserve the legal app or REST trigger shape from the sync plan, then supply stage-appropriate semantic input when the stage requires it. For `Query`, preserve `triggerType`, `parameters.appHint`, `OraUserContext`, `OraAppContext`, REST parameters, and other trigger envelope fields from `suggestedInput`, but choose `input.message` by this precedence: explicit user instruction to use the active run profile; user-provided Query message or Query intent; model-synthesized manager/user question from the app purpose; active run profile; empty message only when intentionally creating limited empty-message Query smoke coverage. Never accept the CLI's default empty Query message as meaningful semantic Query coverage when the workflow or app purpose gives enough context to synthesize a realistic user question. Additionally, `judge.expectedOutcome` for a Query test must describe what a high-quality answer to the synthesized question should contain. Do not copy LLM node prompt sections (`DATA:`, `TASK:`, `OUTPUT:`) or unexpanded `{{$context...}}` expressions into `expectedOutcome`. `InvokeAction` usually requires action identity and minimal action payload/context. `FillParameters` usually requires missing-parameter context for the relevant action. `AdditionalContent` usually requires panel, card, or content context. `InitCommunications` and `SendCommunication` usually require communication context, and mutating send paths remain subject to the existing capture policy. Infer this semantic input from the app, workflow intent, existing ready baseline, or user prompt. If required non-Query app context cannot be inferred safely, do not generate an empty shell test. Report the scenario as blocked input context with the missing context and the exact next step needed from the user, or ask for explicit approval to use model-generated synthetic context.

Before generating a primary-path `record-now` test, check whether the workflow trigger declares named inputs required to exercise that primary path. A required trigger input is unresolved when the workflow trigger declares it, the primary path consumes it in a BO_FUNCTION, CONDITION, or other executable node on that path, and no concrete value exists in the user's original workflow prompt or an existing source-controlled test for this same workflow. Existing tests from other workflows, neighboring workspaces, session memory, CLI examples, help text, BO samples, and plausible values visible in conversation are not valid sources. Treat an unresolved required trigger input like a missing secret or missing environment data: do not infer, guess, reuse, or synthesize a value for primary-path live recording.

If a primary-path `record-now` scenario has unresolved required trigger inputs, stop that scenario and surface a `needs-user-input` action instead of running `do-generate-workflow-test` for it. Name the workflow and blocked scenario, list each missing parameter by name and type when known, and state the exact value needed for live recording. Example: `needs-user-input: Primary-path test for PARALLEL_WORKER_ASSIGNMENT_TEST requires live data recording. The REST trigger declares required input personId (string) with no default in the prompt or existing tests. Provide a valid personId value to proceed with record-now data capture for the primary path.` Make clear that only the `record-now` primary-path recording is blocked.

Alternate-path tests are not blocked by a missing primary-path trigger value when they do not need live recording. You may still create `model-generated` tests with synthetic/sentinel trigger parameters and `testDataOverrides` for empty data, error data, or rare branches. You may also create `baseline-replay` tests after a real baseline exists. Never promote an empty-data or sentinel-parameter case to the primary path, and do not use a synthetic value such as `NO_ASSIGNMENT_PERSON` as the representative `record-now` input.

When the user later supplies the missing trigger value, resume only the blocked primary-path `record-now` scenario using that exact value. Do not modify alternate-path tests that were already created unless the user asks or the workflow changed.

For app-backed workflows, the sync plan may include `appContract` plus app-stage action fields such as `scenarioKind: "app-stage"`, `appStage`, route-specific `expectedPath`, `recordablePath`, and `dataPathSignature`. Treat those fields as authoritative. During app-driven workflow sync, run `do-generate-workflow-test` only for current sync-plan `create` actions and run `do-update-workflow-test` only for current sync-plan `update` actions. Do not invent workflow tests for app panel aliases, panel titles, widget names, app test names, or app-panel validation goals. App panel validation belongs under `test/apps`; workflow tests belong to the workflow sync plan. Create tests only for reachable app-stage actions in the plan; do not fabricate tests for missing or ambiguous app-stage warnings. Preserve each app-stage action's `suggestedInput` trigger envelope so the test uses the same app trigger context the runtime uses, apply the Query message precedence above when the stage is `Query`, and use the route-specific `recordablePath`/`dataPathSignature` when deciding whether `baseline-replay` is valid.

### Terminal Node Output Classification

Before writing output assertions for a test scenario, identify the terminal node — the last node in `pathAssertions.mustExecute` — and apply the matching strategy.

**Class A: semantic-output terminal node**

- Set `defaults.evaluationMode` to `"hybrid"`.
- Do NOT add auto-generated deterministic final-output assertions: `assertions.equals`, `assertions.contains`, `assertions.startsWith`, `assertions.endsWith`, or `assertions.notContains`.
- Semantic-output nodes include `LLM`, `AGENT`, `MULTI_AGENT`, `WORKFLOW`, `RAG_DOCUMENT_TOOL`, and `DOCUMENT_PROCESSOR` when `extractWithLlm` is true. A `RETURN` expression that references output from one of these nodes is also treated as semantic-output.
- Semantic output may be generated, retrieval-answer-like, delegated to another workflow, or otherwise wording-sensitive. Even with replayed file data, it may paraphrase, reformat, or vary its output between runs.
- Prove routing using `pathAssertions.mustExecute` and `pathAssertions.mustNotExecute`.
- Prove output quality using the local judge rubric. Always include the criterion: `"The output is grounded in the replayed test data."`
- Do not act on `assertionSuggestions` from the test runner as literal assertions for these tests. Those suggestions describe what appeared in one run; they are not stable across runs.
- `WORKFLOW` nodes are recordable parent workflow boundaries. Parent tests record and replay the child workflow node output, assert parent routing/final-output behavior, and do not assert child workflow internals. Direct regression coverage for the child workflow belongs in that child workflow's own tests.

**Class B: RETURN node with a hardcoded literal value (no `{{...}}` in returnValue)**

- Set `defaults.evaluationMode` to `"deterministic"`.
- Add `assertions.equals` set to the exact literal string from the node's `returnValue` input.
- Do NOT write a `judge` block — the output is provably exact and the judge will be skipped anyway in deterministic mode.

**Class C: RETURN node with an expression returnValue (contains `{{...}}`)**

- Set `defaults.evaluationMode` to `"deterministic"`.
- Add `assertions.equals` only when the expression value is predictable from the test input. For example: `returnValue = "{{$context.$triggers.REST.$input.my_string}}"` and the test input has `my_string: "abc"` -> `assertions.equals: "abc"` is stable.
- If the expression depends on upstream LLM output or runtime context, leave `assertions` empty.
- Do NOT write a `judge` block.

**Auto-generation default only.** The rule "do not add output assertions to a Class A test" applies to auto-generated assertions during `do-generate-workflow-test`. A user may manually add any assertion type — `equals`, `contains`, `startsWith`, `notContains` — to a Class A test when they know the output characteristic is stable for that specific workflow and prompt. This is a deliberate user choice and must be accommodated without restriction or warning. Manually-added assertions are respected by the runner and must not be stripped by automated update flows.

**Do not auto-repair failing assertions. Do not change the workflow.** If any assertion on a test fails — regardless of assertion type or terminal node class — the model must not do any of the following without explicit user instruction:
- Update or remove the failing assertion to match the observed output.
- Change any workflow node (prompt text, node inputs, edges, conditions, return values) to make the assertion pass.
- Change any LLM node's system prompt or user prompt.
- Remove or add workflow nodes.

When a user-placed assertion fails, report the test name, failed assertion, and final output preview, then stop. Wait for the user to decide whether the assertion, the workflow, or the test data needs to change. Do not suggest a replacement assertion value in the user-facing summary.

Do not add a judge to a Class B or C test; if the JSON schema requires the `judge` field, keep only the inert CLI-generated stub and remember it is skipped in deterministic mode.

Never pass either refresh flag for a request that says run, execute, perform, start, or do the sweep. When the developer asks only to view a previous or latest sweep report, do not run tests and do not recompile; return the existing report link and summarize from the existing result JSON if needed. Run `aistudio propose-sweep-candidates --file <workflow.wf>` when the developer asks which model should be used per LLM node, wants least cost with best quality, or asks whether simple nodes can use cheaper models while complex nodes stay premium. Use `--mode global` only when the developer explicitly asks to compare one model across the whole workflow or asks for a workflow-wide model override experiment.

After creating a fresh sweep config, run every profile suite listed in it before compiling. The judge provider for all profile runs is determined exclusively by the `judgeProvider` field in the sweep config file — never by npm scripts, `package.json` targets, or workspace-level defaults. If the sweep config has `judgeProvider: "local"` or no `judgeProvider` field, run each profile with no `--judge-provider` flag (local is the CLI default) and attach judge results for that run label before starting the next profile. Only if the sweep config explicitly has `judgeProvider: "remote"` should `--judge-provider remote` be passed. For each profile, run `aistudio run-workflow-tests --workflow-code <code> --run-label <profile.label>` and add `--model-overrides @<profile-override-file>` when the profile has `modelOverrides`. Do not run `aistudio run-optimization-sweep --sweep-config <printed-path>` until at least one fresh `run-workflow-tests` execution has completed for every profile label in the current sweep config. If you did not run every current profile label in this turn, do not say you ran or refreshed the optimization sweep; say you only found an existing report and then start or ask to start the fresh proposal flow.

After a global sweep returns `safe-to-downgrade` or `acceptable-tradeoff` model verdicts, offer to drill down with `propose-sweep-candidates --mode node-level`. Explain that a global downgrade can be too blunt because simple nodes may tolerate cheaper models while harder nodes still need premium models.

After a node-level sweep, do not assume individually safe node downgrades are safe together. To validate the Recommended Placement Plan, read `recommendedPlacementPlan.modelOverrides` from the sweep result JSON when present, or fall back to `combinedRecommendedProfile.modelOverrides`, write that object to `recommended-placement.json`, then run `aistudio run-workflow-tests --workflow-code <code> --run-label recommended-node-placement --model-overrides @recommended-placement.json`. For local judge, attach judge results for the `recommended-node-placement` run before deciding whether to apply. For remote judge, run the validation suite with `--judge-provider remote`.

Every optimization sweep summary must include the decision factors a developer needs: recommended model per LLM node when one passed the gates, quality score change, AI-unit/token impact, latency/workflow-time impact, whether the Recommended Placement Plan was validated, and the report path. If no node-level model placement passed the gates, say there are no recommended placements. Also summarize candidate outcomes for models that were tested but not recommended, including quality candidates that held quality but did not reduce AI units or improve latency. Do not label rejected latency tradeoffs as `best placement`, `recommended model`, or `acceptable` in the user-facing summary. Put them under a separate heading such as `Rejected lower-cost candidates` or `Candidate outcomes` and say why they are not recommended, for example latency exceeded the 20% gate, no AI-unit saving was observed, quality dropped, or evidence was missing. If latency was not emitted by runtime reports, say `latency not reported`; do not omit it. If a cheaper model increases latency, call that out plainly so the developer can decide whether the savings justify the response-time tradeoff.

If the Recommended Placement Plan passes validation, end the sweep response by offering the next useful action: "I can apply this validated Recommended Placement Plan to the workflow, then rerun the full workflow test suite and report the final quality, AI-unit/token, and latency impact. I will not apply it unless you approve." Do not leave the developer with only a report path. If the plan fails or was never tested, offer the next useful action to validate the plan or apply model changes one node at a time.

If the developer approves applying a validated Recommended Placement Plan, apply all model placement changes from that plan in one workflow edit, rerun the full workflow test suite, attach local judge results when needed or use remote judge when selected, and then summarize what changed and what was verified: quality/pass status, AI-unit/token impact, and latency/workflow-time impact. If final validation fails or latency regresses materially, say so and stop rather than presenting the workflow as ready.

If the developer asks to apply recommendations from an optimization or sweep report, apply one recommendation at a time and validate after each change, except for a Recommended Placement Plan whose exact model placement map has already passed as described above. For model placement changes, edit the workflow model configuration directly, rerun the suite, attach judge results if needed, and check judge score. If contains assertions fail but judge passes, treat it as assertion drift and read `assertionSuggestions` from the run result JSON to update fragile assertions; do not treat it as a model regression. For structural workflow changes such as node deletion or edge rewiring, re-record affected test data before rerunning the suite. BO over-fetch and grounding-data-excess findings are report-only; do not attempt to modify BO definitions or workflow BO nodes automatically. Do not batch model placement changes with prompt edits, BO changes, or topology changes in one edit.

After attaching judge results and completing the final suite run, call `get-workflow-test-final-summary --file <workflow-file>`. Compose the standalone workflow final response with your concise workflow creation, change, test-generation, or run summary first, then add a section named exactly `Validation and Insights` based on the command output. Preserve test counts, the workflow suite report link, `Metrics:`, and `Optimization:` without omission. Preserve compact issue and next-step guidance when present. Do not hand-write replacement evidence from suite JSON and do not rerun workflow tests merely to refresh reports or summary text. If the command offers optimization, make the action workflow-specific. For run-only requests, summarize what was run and do not use creation language.

Treat failed tests, missing final output, path assertion failures, broad-only assertions, and representative-source-record warnings as feedback that the workflow or tests still need repair, except that semantic-output terminal tests should not be repaired by adding deterministic output assertions. Fix the smallest responsible workflow node, prompt, return binding, path assertion, deterministic assertion, or test data issue, then rerun deterministic checks.

Before repairing, classify the issue as a workflow defect, test assertion defect, test data defect, or nondeterminism/format fragility. Do not change the production workflow's user-facing output contract merely to satisfy a test. Preserve user-requested format, fields, record granularity, tone, exact fallback messages, and data transformations unless the user approves a changed contract. A self-healing workflow prompt repair may make grounding, formatting, and deterministic instructions clearer, but it must not remove required fields, records, branches, sections, or visual/output requirements that came from the user's workflow request. If a test over-constrains real behavior, fix the test or assertions instead of weakening the workflow.

If a REST-trigger test fails because the workflow returns null, routes incorrectly, or appears to ignore a value supplied in `input.parameters`, classify it as a workflow input-binding defect. Inspect `specification.triggers` and repair the workflow expression to `$context.$triggers.REST.$input.<inputName>`. Do not repair by copying the REST parameter value into `input.message`, and do not switch workflow logic to `$context.$system.$inputMessage` unless the original workflow intent was chat-message routing.

When recording or running a test requires the remote DRAFT to match the local `.wf`, never overwrite a newer remote workflow automatically. `do-save-workflow` refetches the saved remote DRAFT and writes that server-normalized content back to the local `.wf`. After local workflow creation or material workflow edits, validate the workflow and save/normalize the local DRAFT once before generating, updating, recording, or running workflow tests so the loop does not pass against a pre-normalized file and drift after a later save. Do not save because a workflow test was generated, updated, judged, or rerun; pure test-only work does not change the workflow DRAFT. Do not save after a workflow suite has passed unless you made a material workflow edit after that pass. Test record/run freshness uses `workflowCode`, `status`, `version`, and `header.ETag`; do not content-hash local JSON against server-normalized JSON. If the CLI reports that the remote DRAFT is not found for the local workflow code, save it with `aistudio do-save-workflow --file <workflow.wf>` without asking for extra confirmation because this creates a new server draft and does not overwrite an existing same-code workflow, then rerun the original record/run command. If the CLI reports a remote/local version or ETag mismatch, compare versions first. Ask the user only when `remoteVersion > localVersion`, because saving local would overwrite a newer remote DRAFT. If both versions are available and `remoteVersion <= localVersion`, do not ask; run `aistudio do-save-workflow --file <workflow.wf>` to save/normalize local, then rerun the original record/run command. If an ETag differs but `remoteVersion <= localVersion`, treat it as stale normalization and save/retry without asking. If versions cannot be parsed or compared, stop and ask because safety is ambiguous. The workflow debug runner may perform one safe save/retry after a pre-node `FAI-40300` remote execution prerequisite error; do not add another manual save loop on top of that retry. Do not manually edit workflow `version` fields. If the user approves overwriting a newer remote with local, use `aistudio do-save-workflow --file <workflow.wf> --overwrite-remote-draft --expected-remote-version <remoteVersion>` before recording or running.

## Flow Selection

- Static literal `RETURN` output: use `assertions.equals` directly when the whole return value is known. No observe pass is needed for exact static terminal messages.
- Semantic-output paths: do not auto-add output assertions. Initial definitions should include path assertions and judge metadata only. Add `contains`, `equals`, `startsWith`, or `endsWith` only when the user explicitly asks for that assertion or when an exact literal marker is explicitly specified as a workflow contract.
- Structural assertions must not be inferred from general behavior. For example, do not add `<html>` merely because the workflow appears to produce HTML, and do not add markdown fences, JSON braces, headings, labels, or section titles unless the exact literal boundary is explicitly required. If unsure, leave the structural assertion out for observe-first.
- When generating alternate static-return tests from a primary semantic-output baseline using `--base-test-file`, clear inherited structural assertions by including `"startsWith": null` and `"endsWith": null` in the definition passed to `do-update-workflow-test`.
- Future regression runs should use `--data-source file` unless the user explicitly asks for `live`. Do not invent `contains` values before seeing data.
- After observing recorded data for a primary-path collection-data presentation or summary, do not strengthen semantic-output terminal assertions from the observed final output. Leave semantic quality, formatting flexibility, derived presentation checks, names, periods, labels, meanings, section headings, and other wording-sensitive expectations to `judge.rubric` unless the user explicitly requests a literal assertion.
- Deterministic assertions must be literal, low-volatility substrings expected in the final output. Do not assert semantic concepts, section ideas, presentation wording variants, or source field names unless the user specifically required those exact words in the final output. If a deterministic assertion fails because of harmless wording or formatting variation, simplify or remove that assertion instead of chasing the new wording. Put semantic quality checks into `judge.rubric` instead. For exact static terminal messages, prefer `assertions.equals` so the whole final answer must match. Add `assertions.equals` only when the expected output is truly static, such as a literal `RETURN` node value or an explicit user-supplied exact assertion. If a `RETURN` node returns an expression like `{{$context...}}`, do not invent `assertions.equals` from the prompt; use stable `contains`, path assertions, and rubric checks unless the exact runtime value is explicitly provided and deterministic.
- User wants real env data now: prefer `--data-capture-policy record-now`.
- User wants structure now and data later: use `--data-capture-policy record-later`.
- User wants no env dependency or synthetic scenarios: use `--data-capture-policy model-generated`. When a ready recorded baseline exists for the same workflow, use `--base-test-file <ready-test-file>` plus `definition.testDataOverrides`; this preserves real node provenance and changes only the branch-forcing node outputs. Use a complete model-generated `testData` object only when no ready baseline exists. If every executable node must be synthetic, still use `--base-test-file` and override each executable node explicitly. Model-generated data must preserve response shape and include fields needed by downstream expressions, prompts, assertions, and judge rubric.
- Scenario changes only runtime trigger context, such as Agentic App `appHint` or REST trigger parameters, and the same recorded data path remains valid: use `--data-capture-policy baseline-replay --base-test-file <ready-test-file>` with an `input` definition and no `testDataOverrides`.
- If a representative `record-now` scenario fails because the live workflow takes a branch that violates `pathAssertions.mustNotExecute`, treat that as a live-data/environment blocker. Do not convert that same representative scenario to `model-generated` data. Report the failed branch, the missing live-data condition, and ask for a suitable user/environment/input or explicit permission for intentionally synthetic coverage.
- Do not invent privacy, sensitivity, HR, payroll, performance, compensation, or employee-data blockers. A domain name, BO name, node name, or field label is not enough to claim live recording is blocked for sensitive data. Say live recording is blocked for privacy or sensitivity only when the user, CLI output, or an explicit policy says so. Otherwise report the actual blocker: missing input, unavailable environment data, fallback branch reached, remote draft mismatch, duplicate app-stage recording risk, or another concrete CLI/runtime reason.
- For app-stage tests with shared recordable data, the representative app-stage scenario must be recorded from real data unless the user explicitly asks for a synthetic suite. Synthetic branch tests for fallback/error paths are allowed, but they must not replace the representative happy-path baseline.
- User asks for the whole flow: get context only when the sync plan is insufficient, generate the definition, materialize, record when needed, run `--data-source file --evaluation-mode deterministic`, inspect reports, repair issues, and rerun deterministic until clean. Then run one final suite pass without `--evaluation-mode`; create and attach local judge results only when that latest suite reports needs-judge cases, and stop on the rebuilt suite report when it shows 0 failed and 0 needs-judge. Run `--data-source live` only when requested.

For fallback, empty-data, and rare-branch tests, every node on the path from the trigger to the intended fallback terminal node must have a valid recorded or generated response in `testData`. Do not generate responses only for the terminal node. Each upstream BO, REST, tool, workflow, or session node whose output is checked by a branch guard must also have a valid response. For example, a "no related records found" test must give the upstream identity or parent-record node a valid `RecordId` so that guard passes, then make the downstream lookup node return an empty collection. If a fallback test routes to an earlier fallback, first verify that `testData` contains a valid response for the upstream node used by that earlier guard. Classify the issue as generated replay data precondition mismatch unless live recording also proves the upstream guard value is genuinely missing after guard expressions and trigger/input shape have been checked.

After a test exists, do not rerun `do-generate-workflow-test` with the same test name. The CLI refuses to overwrite existing test files. Use `do-update-workflow-test` to refresh the test for the current workflow while preserving valid `testData`, apply new model-produced data when the scenario requires it, or create a new test name for a genuinely different dataset.

All workflow test mutations must go through CLI commands. Do not manually patch final files under `test/workflows/` with `jq`, `sed`, Python, editor scripting, or shell redirection. For explicit user-requested assertion updates, write only the changed assertion definition fields to `.debug/<test-name>-assertions-definition.json` and run `aistudio do-update-workflow-test --file <workflow.wf> --test-file <test-file> --definition @.debug/<test-name>-assertions-definition.json` so validation, identity, ordering, and provenance rules are applied consistently.

Workflow test file names and `testName` are user-facing labels, not sync identity. Sync-plan generated tests use the persisted `scenario.id` as durable identity; custom user tests use `scenario.custom = true` and are not owned by sync-plan drift. To rename the report label or clarify test purpose, use `do-update-workflow-test` with only safe display metadata such as `{"testName":"new-display-name","scenario":{"intent":"What this test proves."}}`. Do not change `scenario.id`, `scenario.source`, `scenario.custom`, `scenario.kind`, or scenario-backed `pathAssertions` unless the current sync-plan action requires that update.

When creating or updating a sync-plan generated test from a plan action, include the plan action's scenario identity in the scratch definition if you include any scenario metadata. Use `scenario.id` from the action, write a concise `scenario.intent` in natural language, and keep `scenario.custom` absent or false. Do not derive sync identity from the file name or report label. For user-authored tests that are intentionally outside the sync plan, set `scenario.custom = true` and describe the custom intent.

For false-path, empty-data, rare-branch, and edge-case tests, use the sync plan's `baseTestFile` when it is present. Run `aistudio list-workflow-tests --workflow-code <workflowCode>` only when you are outside the sync loop and need a focused inventory. If no ready baseline exists and the environment can run the primary path, create/record the baseline first. When using `--base-test-file`, copy unchanged baseline nodes exactly except recordable nodes listed in `pathAssertions.mustNotExecute`; omit those skipped nodes from `testData.nodes` because they must not run. Do not relabel copied `raw` nodes as `model-generated`, and do not regenerate copied `model-compacted` nodes. Put only the minimum node responses needed to force the alternate scenario in `testDataOverrides`; those override nodes should normally use `capture.mode = "model-generated"`. `testDataOverrides` must be keyed directly by recordable node code and must never contain a `nodes` wrapper. Do not use `capture.mode = "raw"` inside `testDataOverrides`, and do not override nodes listed in `pathAssertions.mustNotExecute`.

Do not include `jobId`, `finishReason`, or `responseTruncated: true` on nodes with `capture.mode = "model-generated"`. Those fields describe runtime capture provenance; synthetic branch-forcing nodes should have `responseTruncated: false`.

## Scope

Current replay support covers workflows where recordable non-agentic data or workflow-boundary data comes from the explicit recordable allowlist: `BO_FUNCTION`, `EXTERNAL_REST`, `WORKFLOW`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, and `USER_SESSION`.

- Replay only the explicit recordable allowlist: `BO_FUNCTION`, `EXTERNAL_REST`, `WORKFLOW`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, and `USER_SESSION`.
- All other executable nodes run normally unless skipped by `pathAssertions.mustNotExecute`.
- Semantic-output nodes include `LLM`, `AGENT`, `MULTI_AGENT`, `WORKFLOW`, `RAG_DOCUMENT_TOOL`, and `DOCUMENT_PROCESSOR` when `extractWithLlm` is true. Generated tests for paths whose final output depends on these nodes should use path assertions and judge rubrics rather than generated deterministic final-output assertions.
- `WORKFLOW` is both recordable and semantic-output. Record and replay the child workflow boundary result in the parent test, keep child internals out of the parent assertions, and use hybrid judge coverage when parent final output depends on child workflow text.
- `VECTOR_DB_READER` test data uses `metadata: {}` and preserves the node's runtime response shape. Its fixed output is a top-level array of `{ index, text }` items, so downstream references use paths such as `$context.$nodes.SEARCH_POLICY_INDEX.$output[0].text`, not `$output.items[0].text`.
- `DOCUMENT_PROCESSOR` is replayable only when `extractWithLlm` is absent or false. When `extractWithLlm` is true, treat it as semantic output and do not include it in replayed `testData.nodes`.
- TOOL flavors are distinguished by the context `recordableNodeType`: deeplink-backed tools are `DEEPLINK_TOOL`, connector tools are `CONNECTOR_TOOL`, the ORA multi-file built-in is `MULTI_FILE_PROCESSOR`, the ORA user-session built-in is `USER_SESSION`, and `INTENT_CHANGE_INDICATOR` is not recordable.
- EMAIL uses normal node inputs such as `toList`, `subject`, `body`, `ccList`, and `attachments`. Do not look for or invent `emailAccountId`; preserve the EMAIL node's runtime response shape when recording.
- The no-generated-deterministic-assertion rule applies only to generated assertions. Preserve deliberate user-authored deterministic assertions even on semantic-output tests.
- Workflows with no replayable external-data nodes are still testable; their source-controlled test can have ready or pending `testData.nodes = {}` depending on the capture policy.
- Keep all source-controlled test definition and data for one scenario in the single test JSON file.
- Group workflow tests under the lowercase workflow code: `test/workflows/<lowercase-workflow-code>/<test-name>.json`.
- Reports are generated separately under `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.json`, `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.md`, `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.html`, `test-reports/workflows/suite-result.json`, `test-reports/workflows/suite-result.md`, and `test-reports/workflows/suite-result.html`. Reports are runtime output and should not live under the source-controlled `test/` tree.
- When presenting any report link to the user — suite report, per-test report, sweep report, or optimization report — always use the `.html` file path. Never present `.md` (Markdown) report links. The `.md` files are machine-readable intermediates; the `.html` files are the human-facing reports.
- Suite JSON reports include `summary`, `results[]`, `summaryText`, `optimization`, `nextActions`, and failed cases may include `failureSummary`; do not query old/nonexistent fields such as `stats` or `cases`. Use these fields plus the HTML reports to explain all-test runs clearly.
- Final user-facing responses after generating, updating, or running standalone workflow tests must use `get-workflow-test-final-summary --file <workflow-file>` as the evidence source for `Validation and Insights`. Put the workflow creation, change, or sync outcome first. Preserve test counts, the workflow suite report, `Metrics:`, and `Optimization:`. Include compact issue guidance when present; use `--format json` only when the user asks for detailed diagnostics. For run-only requests, do not use creation language.
- For tests that validate summaries or presentations over collection data, assertions and judge rubrics should check that the final answer preserves representative source records and downstream-relevant fields required by workflow intent. Do not accept purely anonymous aggregate output when the intent requires record-level grounding.
- Backend calls are allowed only for `do-record-workflow-test`, `run-workflow-test`, `run-workflow-tests`, and remote workflow freshness checks.
- The standalone CLI cannot invoke an assistant by itself; local model authoring happens before `--definition` or `--test-data` is passed to the CLI.

## Capture Policy And Runtime Data Source

- `--data-capture-policy record-later`: omit `testData`. The CLI creates `testData.status = "pending"`, `capturePolicy = "record-later"`, and node shells for every recordable node.
- `--data-capture-policy record-now`: omit `testData`. The CLI runs the workflow debug endpoint live and writes the test file with filled `testData` when each node response is complete valid JSON and within the size budget.
- `--data-capture-policy model-generated`: when no recordable nodes exist, the CLI can create ready empty `testData.nodes = {}` without a supplied `testData` object. Otherwise, either include complete `testData` with `status = "ready"`, `capturePolicy = "model-generated"`, and a response for every recordable node that can execute in the asserted path when no ready recorded baseline exists, or pass `--base-test-file <ready-test-file>` and include only `testDataOverrides` for the nodes that must change. Omit recordable nodes listed in `pathAssertions.mustNotExecute`. The local assistant generates this data from user intent and workflow context; the CLI validates it but never invents missing data. If a ready `record-now` baseline exists and a full `testData` object is supplied without `--base-test-file`, generation fails so real upstream node provenance is not lost.
- `--data-capture-policy baseline-replay`: pass `--base-test-file <ready-test-file>`, supply only the changed `input`/assertion/path/judge metadata, and omit `testData` and `testDataOverrides`. The CLI copies the baseline node data exactly, sets `testData.capturePolicy = "baseline-replay"`, and changes only runtime invocation context.
- `--data-source file`: replay embedded `testData`. This is the default for CI and local regression tests.
- `--data-source live`: call the environment and ignore `testData`.

## Smart Recording And Compaction

The CLI records raw data only when the captured response is complete, valid, not backend-truncated, unmodified, and small enough. Each recordable node response should stay around 2 KB to 3 KB. The implementation limit is 3072 bytes per recordable node `response`; the limit does not apply to `input`.

If recording sees backend-truncated output, invalid JSON, missing output, or oversized output, it must not write that output as test data. Instead it writes `.debug/<test-name>-test-data-request.json` and returns `needs-model-test-data`.

For recorded data, keep runtime capture provenance under `capture`: `mode`, `responseTruncated`, optional `jobId`, and optional `finishReason`. Do not put `jobId` or `finishReason` in node `metadata`; `metadata` is for stable node identity such as `businessObjectCode`, `externalRestToolCode`, and `functionName`.

When that happens:

1. Read the request file and workflow context.
2. Prefer a node-level payload shaped as `{ "nodes": { "NODE_CODE": { "capture": { "mode": "model-compacted", "responseTruncated": true }, "input": {}, "response": {} } } }`.
3. Include only nodes listed in `nodesNeedingModelData`; the CLI starts from `testDataTemplate` and preserves `rawNodesToPreserve` exactly.
4. Use a complete `testData` object only when every node must be supplied manually or the node-level payload is insufficient.
5. If producing a complete `testData` object, start from `testDataTemplate`, copy every `rawNodesToPreserve` node exactly, and replace only nodes listed in `nodesNeedingModelData`.
6. Prefer fields referenced by downstream `CODE`, `LLM`, and `AGENT` nodes, assertions, and judge rubric.
7. Remove unused fields, large links, context metadata, and irrelevant nested data.
8. Preserve the response shape expected by the workflow.
9. For collections, prefer multiple narrow representative items over one wide item. When the request preview exposes multiple rows, keep 2 to 5 compact rows that preserve meaningful variety across fields the workflow actually uses, such as distinct categories, statuses, dates, numeric values, boolean states, or descriptive text.
10. Reduce fields before reducing record count. Drop downstream-irrelevant fields from all records before reducing the number of records. A field is downstream-irrelevant when no downstream CODE, LLM, or AGENT node prompt, expression, assertion, or judge rubric criterion references it. Only reduce record count if field reduction alone is still insufficient to meet the response budget.
11. For rating, scoring, or classification collection data where the workflow final output must represent each unique entity, compaction must retain at least one record from each distinct value tier of the primary metric that exists in the preview data. For example, if the preview shows primary metric tiers 1, 3, and 5, keep all three tiers represented even if only one record per tier survives. Dropping the highest or lowest tier removes grounding data and makes judge verification impossible.
12. Prefer fewer downstream-relevant fields across multiple rows over many technical fields from a single row. For LLM-consumed data, prioritize fields named in the LLM prompt, assertions, and judge rubric; drop `@context`, `links`, large IDs, and unrelated technical fields unless downstream logic explicitly references them.
13. Adjust envelope fields such as `count`, `limit`, `offset`, `hasMore`, and `links` to match the compacted collection. For compacted or generated collection snapshots, set `count` to `items.length`, set `hasMore` to `false`, keep `limit` greater than or equal to `items.length`, keep `offset` non-negative, and use an empty `links` array or omit links unless downstream logic consumes it.
14. Use `capture.mode = "raw"` only when the recorded response is complete, valid JSON, not backend-truncated, unmodified, and under the response budget.
15. For `record-now` requests, captured preview rows are real environment data. If any usable real row or field is present but the response cannot be stored as-is, keep `testData.capturePolicy = "record-now"` and use `capture.mode = "model-compacted"` for that node. Do not switch to `model-generated` merely because the preview is truncated or oversized.
16. For `model-compacted` collection data, first try to keep 2 to 5 real representative rows by trimming fields based on downstream usage and the response budget. Keep one real row only when multiple compact real rows cannot fit or cannot be reconstructed safely from the available preview/context. For a node with `capture.mode = "model-compacted"`, always set `capture.responseTruncated: true`. The CLI canonicalizes `capture.mode = "model-compacted"` to `capture.responseTruncated: true` during apply/create/update, but set it correctly up front. Model-compacted means the original response exceeded the response budget and was reduced; the stored subset never represents the complete environment response. `responseTruncated: false` is correct only for `raw` captured nodes (complete, unmodified, under-budget response) and `model-generated` nodes (synthetic data with no real environment source).
17. Use `capture.mode = "model-generated"` only when no usable real response rows or fields are available, or when the user intentionally requested synthetic model-generated data.
18. Treat `outputSpecification` as shape guidance, not a mandate to keep every property. Keep the collection envelope and downstream-relevant fields; omit schema-listed fields that downstream logic, assertions, and judge rubrics do not consume.
19. Apply the node-level payload or complete `testData` object with `aistudio do-apply-workflow-test-data --test-file <test.json> --test-data @.debug/<test-name>-test-data.json`. Add `--cleanup-scratch true` when the request and produced data files are no longer needed.

Never include backend-truncated `.....` previews in `testData`. Keep each node `response` around 2 KB to 3 KB or less.

`.debug/` is temporary, gitignored local scratch space for authoring definitions, compaction requests, model-produced test data, and judge drafts. Name workflow-test scratch files with the test-name prefix, such as `.debug/<test-name>-definition.json`, `.debug/<test-name>-path-update-definition.json`, `.debug/<test-name>-test-data.json`, and `.debug/<test-name>-judge-result.json`, so `do-apply-workflow-test-data --cleanup-scratch true`, `attach-workflow-test-judge-results --cleanup-scratch true`, and `attach-workflow-test-judge-result --cleanup-scratch true` can remove them. A ready test must not depend on `.debug/`; the durable source of truth is only `test/workflows/<lowercase-workflow-code>/<test-name>.json`.

When cleaning up `.debug/` scratch files not covered by `--cleanup-scratch true`, such as BO search result files written with `--write-result`, scratch definition files, and compaction files, use shell `rm` to delete the files rather than editing them to empty content. Editing a file to empty can flood the conversation log with deleted JSON content. `do-apply-workflow-test-data --cleanup-scratch true` covers test-data request and response files; `attach-workflow-test-judge-results --cleanup-scratch true` covers judge-specific files. Remove any remaining scratch files with `rm .debug/<file>` or `rm .debug/*.json` at the end of the session.

Before running any git command such as `git status`, `git log`, or `git diff`, verify that a `.git` directory exists in the workspace root. If no `.git` directory is present, skip all git commands silently and omit any git-based workspace summary from the final response.

If `testData.status = "pending"`, the test was created with `record-later` or recording did not complete. Record real data with `aistudio do-record-workflow-test --test-file <test.json>` or apply model-produced test data before running with `--data-source file`.

## Rules

- `defaults.dataSource` must be `file` or `live`; prefer `file`.
- `defaults.evaluationMode` must be `deterministic` or `hybrid`; prefer `hybrid` when final output depends on a semantic-output node and semantic evaluation is needed. Use `deterministic` for static-return tests whose `assertions.equals` fully verifies a fixed, hard-coded output string.
- `input` must be an object. `input.message` must be a string and may be empty for non-chat trigger types.
- `input.triggerType` is optional. Omitted or `chat` means normal chat-style execution. Non-chat values include `app`, `rest`, `email`, and `schedule`.
- `input.parameters` is optional and must be a JSON object when present. Use the debug API field name `parameters`, not `params`.
- `input.singleTurnOnly` is optional and must be boolean when present. Set it only when the matching run profile would set it, such as REST, email, or schedule invocations.
- `testData.status` must be `pending` or `ready`.
- `testData.capturePolicy` must be `record-later`, `record-now`, `model-generated`, or `baseline-replay`.
- `capture.mode` must be `raw`, `model-compacted`, or `model-generated`.
- `assertions.contains` and `assertions.notContains` must be arrays of strings.
- `assertions.equals` is optional and should be used for exact whole-output checks, especially literal static fallback or early-return messages. Do not auto-add `assertions.equals` for expression-backed `RETURN` nodes because the exact runtime text comes from evaluated context.
- `pathAssertions` is optional. Use `mustExecute` and `mustNotExecute` to prove true branches, false branches, early returns, empty-data paths, and other structural behavior. Use exact executable behavior node codes from the sync plan, `get-workflow-test-context`, or `get-workflow-test-scenarios`. Do not include structural workflow nodes in `pathAssertions`; the CLI ignores persisted workflow nodes whose type is `START`, `END`, or legacy `ADD`. Runtime/debug events such as `NODE_START` and `NODE_END` are not workflow node codes.
- For sync-plan create/update actions, the sync plan's `expectedPath` is authoritative. When the visible action row includes `expectedPath`, copy it exactly into `definition.pathAssertions`; do not shorten it or omit `mustNotExecute`. When a focused next action exposes only `authoringHints` and omits the bulky `expectedPath`, omit `definition.pathAssertions` and preserve the scenario id or test name so the CLI rehydrates the full expected path from the sync plan. Never write empty, partial, or guessed `mustExecute`/`mustNotExecute` arrays to save tokens.
- For sync-plan `update` actions, do not preserve stale or narrower `pathAssertions` from the existing test. Use the current action's `expectedPath` when it is shown; otherwise omit `definition.pathAssertions` and let the CLI refresh it from the scenario id or test name. If live execution proves a different path, stop and report the observed routing mismatch instead of silently changing a scenario-backed path.
- WHILE paths in the sync plan are topology-derived and represent the body-entering path. Do not infer a separate zero-iteration WHILE test from topology alone; create one only when the user explicitly asks for it or an observed run/debug result proves the body was skipped, and keep `pathAssertions` consistent with that observed path.
- Exhaustive `mustNotExecute`: for any alternate-path test, `mustNotExecute` must list every workflow node that will not execute on that path, including CONDITION nodes, all RETURN nodes for other paths, and all nodes downstream of the early-exit point. Do not limit `mustNotExecute` to only BO_FUNCTION and LLM nodes. Derive the complete list by tracing the workflow from the exit node to the end and listing every node that is bypassed, plus all sibling RETURN nodes that belong to other alternate paths.
- `judge.minimumScore` must be an integer from 1 to 5; prefer 4.
- `judge.rubric` must be an array of strings. Do not include a rubric criterion that re-checks deterministic assertions such as "final answer satisfies the stable deterministic assertions", exact `startsWith` or `endsWith` boundaries, or exact `contains` values. Rubric criteria should cover semantic output-contract requirements that deterministic assertions cannot verify.
- Static-return judge rubric: when a test uses `assertions.equals` because the entire workflow output is a fixed, hard-coded string from a RETURN node, set `judge.rubric` to exactly one criterion: `"The workflow output exactly matches the expected static message for this error or boundary condition."` Do not use the multi-criterion LLM-output rubric for static-return tests. The `assertions.equals` check already covers correctness deterministically; the judge rubric must reflect what the judge is actually evaluating.
- `evaluationMode` for static-return tests: when a test uses `assertions.equals` because the entire workflow output is a fixed, hard-coded string from a RETURN node, set `defaults.evaluationMode` to `"deterministic"`. The `assertions.equals` check fully verifies correctness; a judge adds no additional coverage for a known static string and wastes tokens. Reserve `"hybrid"` for tests where final output depends on a semantic-output node and semantic evaluation is needed.
- `testData.nodes` must include every current executable recordable node (`BO_FUNCTION`, `EXTERNAL_REST`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, or `USER_SESSION`) in the asserted path and must not include stale node codes. It may be `{}` when the workflow has no recordable nodes. A current recordable node may be omitted only when listed in `pathAssertions.mustNotExecute`; skipped nodes should have no fake placeholder data.
- Data node properties must be ordered as `nodeType`, `capture`, `metadata`, `input`, `response`.
- Use node codes exactly as shown in `get-workflow-test-context`.
- Use the workflow code namespace exactly as shown in `get-workflow-test-context`.
- Keep chat-style `input.message` short, user-facing, and concrete enough to invoke the workflow. For non-chat scenarios, preserve the sync-plan `suggestedInput` or active run profile trigger fields. Do not copy internal node prompts, `TASK:`/`OUTPUT:` prompt sections, workflow context expressions, test data, assertion text, or judge rubric text into `input.message` or `input.parameters`.
- Avoid assertions that depend on changing dates, IDs, or volatile wording unless the user's prompt explicitly asks for them.

## Judge Rubric Rules

`judge.expectedOutcome` must be a human-readable output contract description. Write `judge.expectedOutcome` as a self-contained description of what a high-quality final answer should contain and accomplish, derived from the workflow description and the original user request. Do not copy LLM node prompt text, TASK/OUTPUT sections, or unexpanded `{{$context...}}` runtime expressions into `expectedOutcome`. The judge evaluates actual final output text; unexpanded runtime expressions and raw prompt templates are not meaningful in that context.

For any test where final output depends on a semantic-output node, always include an explicit `judge` block with a hand-authored `expectedOutcome` in the scratch definition passed to `do-generate-workflow-test` or `do-update-workflow-test`. Do not rely on the CLI's auto-generation from `--prompt` alone to produce `expectedOutcome`; the CLI may derive it from workflow metadata and include raw node prompt text with unexpanded `{{$context...}}` expressions. If `--prompt` was used without `--definition` for the initial scaffold, immediately follow up with a `--definition` update that includes a corrected `judge.expectedOutcome` before proceeding to the observe step.

After generation, immediately verify the persisted test file's `judge` block before cleanup can remove the scratch definition. If `judge.expectedOutcome` contains unexpanded runtime expressions, raw LLM prompt sections, or the auto-generated workflow-contract prefix, replace it with a self-contained plain-English output contract. If a deterministic test or a test with `assertions.equals` has more than one `judge.rubric` criterion, replace the rubric with the single static-return criterion. If a hybrid test has fewer than two substantive quality criteria, repair the judge block with criteria that cover the semantic output contract. Apply repairs through `do-update-workflow-test --definition`, not by hand-editing the test file. Skip the update when the persisted `judge` block already passes these checks.

For primary-path semantic-output tests, derive `judge.expectedOutcome` and `judge.rubric` from the workflow output contract: the workflow description, relevant semantic-output node prompts or descriptions, and the original workflow creation request when available. The expected outcome should summarize the complete output contract, not just the test generation prompt or a structural boundary.

Never add a redundant deterministic criterion. Criteria such as "Final answer satisfies the stable deterministic assertions", "Output starts with X and ends with Y", or "Output contains the expected values" duplicate checks that already ran before judge evaluation and must be omitted.

Write one independently verifiable criterion for each distinct semantic requirement that deterministic assertions cannot prove. Prefer criteria for content coverage, required sections or output categories, preservation of required entities/records/fields/transformations, and grounding against replayed `testData` and executed node results. Avoid vague criteria such as "output is well-formatted" or "output is useful" unless the workflow contract defines exactly what that means.

## Local Judge Result Contract

`hybrid` evaluation runs deterministic assertions first. With the default `local` judge provider, if deterministic checks pass, the CLI writes `.debug/<test-name>-judge-request.json` for normal runs or `.debug/workflow-test-runs/<safe-run-label>/<test-name>-judge-request.json` for run-labeled model comparison runs, marks the run `needs-judge`, and prints the attach command. In that default route, the CLI does not call an LLM, the live environment, the workflow debug API, or a backend Builder API for judging. The assistant must read the request, evaluate the final output against `judge.expectedOutcome` and `judge.rubric`, and write the matching `<test-name>-judge-result.json` next to the request file. Prefer `aistudio attach-workflow-test-judge-results --workflow-code <workflowCode> --cleanup-scratch true` for normal suites and add `--run-label <label>` for run-labeled suites whenever one or more judge requests exist, even when there is only one pending judge request. The CLI attaches all available judge results and rebuilds suite JSON/Markdown/HTML from individual reports in one pass. Use `attach-workflow-test-judge-result` only for a targeted single-report repair. Treat the suite report rebuilt by the attach command as authoritative final validation when it reports 0 failed and 0 needs-judge; do not run another default/hybrid suite pass just to confirm the attach. Judge results can be attached only to pending `needs-judge` hybrid reports.

When `run-workflow-test` or `run-workflow-tests` uses `--judge-provider remote`, the CLI still writes the judge request file for audit, then calls the configured FA environment, validates the returned judge JSON, writes the matching judge result file, and marks the test passed or failed in the same run. Remote judging uses the environment default model; do not pass judge model overrides or try to select a judge model.

When attaching a local assistant judge result, write strict JSON with exactly this accepted shape. The array field must be named `criterionResults`; names such as `rubricResults` or `results` will be rejected. `unsupportedClaims` must always be present as an array; use `[]` when there are none. Top-level `passed` must be `true` when `score >= minimumScore` from the test file, and `false` otherwise. Include one `criterionResults` entry for each criterion in `judge.rubric`. Do not use a top-level `findings` array instead of `criterionResults`.

Before writing `.debug/<test-name>-judge-result.json`, self-check all five required top-level keys: `score`, `passed`, `summary`, `criterionResults`, and `unsupportedClaims`. The field names `criteria`, `rubricResults`, `results`, and `findings` are wrong and will cause attach to fail; per-criterion details belong in `criterionResults` entries. `unsupportedClaims` must always be present as an array, even when empty (`[]`). Inside each `criterionResults` entry, use `criterion`, `passed`, and `notes`; do not add a per-criterion `score` field. Start from the `judgeResultTemplate` in the judge request file and fill in the values instead of constructing the shape from memory.

```json
{
  "score": 5,
  "passed": true,
  "summary": "The final output satisfies the judge rubric and stays grounded in the replayed workflow data.",
  "criterionResults": [
    {
      "criterion": "<criterion text from the test rubric>",
      "passed": true,
      "notes": "<brief justification>"
    }
  ],
  "unsupportedClaims": []
}
```
